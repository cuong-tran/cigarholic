# Backup and restore

Nightly production backup to Backblaze B2, 30-day retention, snapshot before every production deploy,
one restore drill into staging before launch (OPS-07). Scripts: `infra/backup/`.

## What is backed up

| Backup | What | Where | Retention |
| --- | --- | --- | --- |
| Nightly (`cigarholic-backup.timer`, 03:17 UTC) | `mariadb-dump --single-transaction` of the production database + tar of `shared/web/app/uploads` + manifest | `b2://<B2_BUCKET>/production/<timestamp>/` | 30 days: bucket lifecycle rule (owner sets "keep only the last version, delete after 30 days") plus `rclone delete --min-age 30d` after each run |
| Local copy of the nightly dump | database only | `/var/www/production/shared/backups/nightly-<timestamp>/` | 3 days |
| Pre-deploy snapshot | database | `/var/www/production/shared/backups/pre-deploy-<timestamp>.sql.gz` | last 10 |

Not backed up: `shared/.env` (regenerated by `site.sh`, keys re-upserted by the deploy workflow), the
code (Git), `vendor/` (Composer).

## Credentials

`B2_BUCKET`, `B2_KEY_ID`, `B2_APPLICATION_KEY` (secrets) and `B2_S3_ENDPOINT` (variable) live in
GitHub. The timer on the server needs them locally: the first `backup-production` run of
`backup-restore.yml` while `SSH_USER` is `root` writes them to `/etc/cigarholic/backup.env`
(root, 0600). Until then the timer exits with code 2 ("not configured") and shows as failed in
`status`, which is intended. Rotate by changing the GitHub secret and running `backup-production`
again as root.

## Run a backup now

```bash
gh workflow run backup-restore.yml -f action=backup-production
gh workflow run backup-restore.yml -f action=list
```

On the server: `sudo systemctl start cigarholic-backup.service && journalctl -u cigarholic-backup -n 50`.

## Restore drill: production into staging

```bash
gh workflow run backup-restore.yml -f action=restore-production-to-staging -f backup=latest
```

`infra/backup/restore.sh <timestamp|latest> --to staging` downloads the backup, snapshots the
staging database first, drops and imports the tables, runs `wp search-replace` from
`https://cigarholic.com` to `https://staging.cigarholic.com` (all tables, GUIDs kept), rsyncs the
uploads, then re-asserts staging safety: `blog_public 0`, Stripe `testmode` with live keys deleted
from `woocommerce_stripe_settings`, PayPal `sandbox_on` with live credentials deleted from
`woocommerce-ppcp-settings`, `wp cigarholic provision`, cache flush. Afterwards run
`health-check.md` against staging and record the drill in `docs/STATUS.md`.

Restoring into production is refused unless `--i-know-this-overwrites-production` is given and is
deliberately not offered by the workflow: it is an owner decision, done from the console or a laptop.

## Restore a local dump (database only)

As `deploy` on the server, after the owner's go:

```bash
cd /var/www/production && bash current/infra/backup/snapshot.sh production
set -a; . shared/.env; set +a
gunzip -c shared/backups/pre-deploy-<timestamp>.sql.gz | mariadb -u "$DB_USER" -p"$DB_PASSWORD" "$DB_NAME"
wp --path=current/web/wp cache flush && sudo -n /usr/local/sbin/cigarholic-cache-purge production
```

## Verify

- `backup-restore.yml` → `list` shows a folder per night; `status` in `infra-provision.yml` shows
  the last upload under "last B2".
- Quarterly: a restore drill into staging; the result goes into `docs/STATUS.md`.
- Owner: the B2 bucket has the lifecycle rule and the application key is restricted to that bucket.
