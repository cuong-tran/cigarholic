# Changelog

All notable changes to Cigarholic. Format: [Keep a Changelog](https://keepachangelog.com/en/1.1.0/); entries name their feature IDs from `docs/FEATURES.md`. Releases are Git tags deployed to production after the owner's approval.

## [Unreleased]

### Added

- SEO-01: a site that discourages search engines (`blog_public` 0: staging and development, from `DISALLOW_INDEXING`) answers robots.txt with `User-agent: *` / `Disallow: /` (`Seo\RobotsTxt`, toggle `robots-txt`, on; last on the `robots_txt` filter). WordPress stopped writing that line itself in 5.3 and relies on the noindex meta tag alone, so staging's robots.txt would otherwise have listed only `/wp/wp-admin/`. Public sites (production) keep WordPress's rules plus what WooCommerce and SEOPress add. `RobotsTxtTest`.

- CNT-01 / CMP-04: `ThemeContrastTest` checks every text colour declared in `theme.json` and every `styles/` partial against its background (4.5:1), the palette rules (which text colours each ground allows), the email colour pairs, and that WordPress registers the Forest style for groups and columns. `tests/e2e/brand.spec.js` checks that both fonts are served by the theme, load and actually paint the H1 (Chromium's platform-font report), that nothing is requested from Google Fonts, the Forest ground, the Gold focus ring and the Forest error colour, and AA contrast of every visible text on the coming-soon page, the home page and the shop. It found Cedar links on the canvas's board colour Sand at 4.27:1, so Sand did not become a token. Text over a background image, gradient or Cover block is reported for a manual check instead of passing unchecked. `ThemeContrastTest` also checks the PHP-registered block styles (Card, Eyebrow) on light and on Forest. FND-03 / CNT-04: provisioning step 80 warns when a coming-soon template saved in the Site Editor hides the theme file (it never deletes it).

- CNT-01 / ORD-03: the owner's logo. The wordmark is taken from the supplied artwork (a checkerboard painted into the pixels, so it was separated by colour with soft edges kept; the "by MaX2lab" lines left out) with masters in `brand/`. Provisioning step `25-brand` imports the logo (WebP) and the site icon (the C on Forest, 512 px PNG, core's 32/180/192/270 sizes, kept PNG for iOS) into the media library once per file version (SHA-256), together with the email logo (a 400 px PNG shown 200 px wide, an upload so its URL survives a code rollback), and sets `site_logo`, `site_icon` and the WooCommerce email header image. A copy that is deleted, trashed or edited in the media library is imported again, and alt text and the site-icon marker are enforced on every run. The header shows the logo instead of the site title; the coming-soon page shows it above the H1, now the "Handcrafted humidors" label (Eyebrow works on headings too). `ProvisionTest` (imported once, PNG icon, email logo) and `brand.spec.js` (logo loaded with its alt, favicon and apple-touch-icon PNG).

### Changed

- CNT-01 / CNT-04 / CMP-04 / ORD-03: the owner's brand system replaces the placeholder tokens (ADR 0009, plan `docs/plans/CNT-01-brand-style.md`, PR 1 of 5). `theme.json`: Ash ground, Ash tint panels, Stone, Ink, Cedar links and buttons, new `forest`, `forest-2`, `mist`, `gold` and `line` slugs; Young Serif (headings, weight 400, no synthesized bold or italic) and Hanken Grotesk (everything else) self-hosted from Fontsource 5.3.0 (latin woff2 with OFL licences in `assets/fonts/`, preloaded, nothing requested from Google); a new type scale up to a 40–64 px H1; flat surfaces (the `soft` shadow is gone), 3 px buttons. New section style **Forest** (`styles/sections/forest.json`) for dark sections, with the focus ring, form error colour and eyebrow label switching with it (`style.css` custom properties); block styles **Eyebrow** (new) and **Card** (now Ash tint with a Line border and Ink text, and a light surface inside Forest too: its headings, links and focus ring follow the light rules there). The coming-soon page, the only page visitors see on production, is now a full Forest page with the Young Serif name, a Gold label, Mist text and a Gold signup button. Transactional emails: Forest header, Ash outer, Ash tint body (provisioning step 70; deploys update existing sites). Signup and contact errors use `#f2a08a` on Forest (7.11:1); the signup form heading is one size below an H2. Header, footer, homepage and WooCommerce pages keep their layout until PRs 2 to 4 but already use the new tokens.

### Fixed

- SEO-01: `/robots.txt` and the XML sitemaps answered Nginx's own 404 on both VPS sites (found on production after `v0.1.1`): the vhost's static-asset regex caught every `.txt` and `.xml` and found no file, because WordPress builds them in `index.php`. `site.conf.tpl` now routes `/robots.txt` (exact match) and the core and SEOPress sitemap names (`/sitemap.xml`, `/wp-sitemap*.xml`, `/sitemaps.xml`, `/<type>-sitemap<n>.xml`, `/sitemap_index.xml`) to PHP ahead of that regex, through the same FastCGI cache rules and headers as other pages; real files of those names are still served directly, the hard denies still win, staging keeps basic auth and `noindex`. The Compose runtime never listed `txt` or `xml` as static and needed no change. `tests/infra/nginx-staging-auth.sh` now runs every hard deny and the new locations with the static regex in template order (69 cases, 40 before), and `tests/e2e/robots.spec.js` checks `/robots.txt` on the Compose stack. Reaches the servers through `infra-provision.yml` → `site-staging` and `site-production`, not through a release: applied to both on 2026-11-03 (runs 41599252862, 41599367782); production now serves `/robots.txt` and SEOPress's `/sitemaps.xml` with HTTP 200.

## [0.1.1] - 2026-11-03

Post-launch hardening of the coming-soon site. Tagged by the owner at `813d144` and deployed to production the same day (release 3, approved on the `production` Environment): no administrator login name for visitors, the installer's sample post removed, two-factor required for administrators and shop managers.

### Added

- OPS-07: two-factor authentication is required for administrators and shop managers (`Security\TwoFactorRequired`, toggle `two-factor`, on). A privileged account without a method gets a 3-day grace period from its first login, with a notice naming the deadline; after it, the account keeps only `read` and the admin dashboard, so its profile (where the Two Factor setup lives) is the only admin page and the REST API, admin-ajax, admin-post and application passwords refuse store management. Enrolling restores everything at once; roles are never changed. Provisioning step `45-two-factor` offers Authenticator App and Recovery Codes only (emailed codes would lock managers out while there is no transactional mail). Runbook `docs/runbooks/two-factor.md`, manager guide section, `TwoFactorRequiredTest`.

### Fixed

- OPS-07: no login name reaches a visitor after a fresh install. `?author=N` no longer redirects to `/author/<login>/`, author archives answer 404, author links on the front end point at the home page, the core users sitemap is gone, and feeds (`dc:creator`) and oEmbed cards show the site name while a user's display name is still the login. Found on production right after the `v0.1.0` install: `/?author=1`, `/feed/` and `/wp-json/oembed/1.0/embed` named the administrator.
- FND-03: provisioning (`20-pages`) trashes the installer's untouched "Hello world!" post, which was public in the feed, the REST API and oEmbed during coming-soon, together with its sample comment.
- CNT-04: `cigarholic-core` no longer touches the signups table while WordPress is being installed (`init` runs during `wp core install`, before `wp_options` exists; seen as a database error in the production install log and in the 2026-11-02 staging review).

### Fixed

- Docs (#43): the manager guide said two-factor is required; the Two Factor plugin is active but enrolment is not enforced yet (OPS-07, next actions).
- FND-08 / OPS-01 (#31), from the first real runs on the VPS: `infra-provision.yml` reads `LETSENCRYPT_EMAIL` from the repository secret or the variable; the deploy sudoers file no longer sets `requiretty` (sudo on Ubuntu 26.04 rejects it, which stopped `provision.sh` at the visudo check); `status.sh` prints `-` for tools that are not installed yet.
- FND-08 (#34): the first staging deploy failed its health check with HTTP 500 because MariaDB rejected the password in `shared/.env`: `random_secret` in `site.sh` had a `}` inside its `${2:-...}` default, so `:,.<>?-}` was appended to every charset and the `?-}` range added the backslash, which MariaDB reads as an escape and PHP literally. Secrets are now alphanumeric; `site.sh` rotates a non-alphanumeric `DB_PASSWORD` and re-asserts the database user (both sites were affected and rotated). `wp` on the server is a wrapper that silences WP-CLI 2.12's PHP 8.5 deprecations for the CLI only.
- FND-03 (#41): staging reported `blog_public = 1`: `DISALLOW_INDEXING` was defined for staging and development but nothing read it (the Bedrock plugin that does is not installed). Provisioning now sets Settings > Reading > search engine visibility from the constant; production stays visible. Staging was never indexable in practice (basic auth and `X-Robots-Tag: noindex`).
- FND-08 (#40): the deploy activates the plugins (WooCommerce first, then every plugin the `--no-dev` release installed) before `wp wc update`; the first deploy after `wp core install` on staging failed with "'wc' is not a registered wp command" because a fresh install activates none.
- FND-08 (#35): the #34 generator (`tr </dev/urandom | head -c`) exited 141 under `pipefail`; it now reads a finite 4 KiB and loops. `tests/infra/site-secret.sh` runs the shipped code under strict mode in CI.

### Security

- FND-08 (#39): `wp-cli.yml` loads the owner email and initial password from secrets only, and only for a command that references them; `infra-provision.yml` reads `LETSENCRYPT_EMAIL` from the secret only. A repository variable's value is printed in the logs of this public repository.
- OPS-07 / FND-08 (#36, 2026-11-02): the staging basic-auth exemptions for payment webhooks matched URI prefixes, so `/wp/wp-admin/install.php?wc-api=x` and `/wc-api/../wp/wp-admin/install.php` reached the WordPress installer of the freshly deployed, not yet installed staging site without credentials (verified from outside, HTTP 200). Staging was taken offline within minutes (the `current` symlink removed; no install had happened, the database was still empty). The exemptions now match whole URLs with no `.`, `%` or extra query string, `install.php` and `setup-config.php` are denied on both sites, and `tests/infra/nginx-staging-auth.sh` checks 31 cases against a real Nginx in CI. Evidence afterwards (`status`, #37): the staging database held only `wp_cigarholic_signups` (WordPress never installed) and the access logs show five installer requests, all GET, all from the verification probes; no POST.
